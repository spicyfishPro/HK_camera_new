# 逐田间行采集与拍照进度（2.5）

每张主图保存成功后上报元数据，不上传图片。每个挂牌对应独立田间行：麦穗每行 Rep1–5 各正、侧面，共10张；籽粒每行 Rep1–3。采样 Rep 与种植区段的田间重复是两个字段。CK 不采集、不计应拍进度。

## 开始与命名

选择“扫码识别”或“手输挂牌号”，两者均需现有挂牌 Bearer 密钥及联网解析。不能只输入材料编号启动。核对界面显示的种植表来源、本次群体、当前成员号、Material名称、田间行号、挂牌号与田间重复后拍摄。

升级后选择新的空根目录。根目录绑定具体种植表ID、年份、地点；同一根目录不能混用不同种植表。照片直接保存在 `本次种植群体_麦穗或籽粒_拍摄人` 文件夹，文件名为 `当前成员编号_行号_RepN_视角`，例如 `RIL8_行1_Rep1_front.png`。无群体材料使用“无群体”目录及 CS、MX1 等独立材料标识或当前Material名称。挂牌号只保存在元数据，不进入照片名或子目录名。

`.capture-context.json` 和 `.capture-rows.json` 保存真实群体、账号及种植行归属，应与照片一并保留。只有同一田间行可沿用其前缀续拍；另一行的同名材料不会继承进度。编号或行号改变时会提示沿用该行已有前缀和格式，不自动改写旧照片。首次遇到无归属的既有同名前缀文件时停止，不猜测续拍。运行中的工作流固定身份、目录和格式。

图片XMP使用 `wheat.capture.v2`，分别保存当前编号、文件前缀、种植行、Material、成员、本次群体、区段、田间重复及来源依据。旧档案匹配与已确认来源不混用。

## 断网、重启和旧数据

已开始的田间行可断网继续拍，队列持久保存；切换挂牌或重启后续拍必须联网重新核验。待同步队列仍保留原capture_id及拍摄人；重新输入原密钥或经核验属于同一账号的新密钥后补传。其他账号不能接管旧记录。队列写失败时明确提示，修复后重试。

旧照片、旧目录和旧队列不删除、不自动迁移。不能将旧材料名前缀文件直接算作新田间行已拍。平台只知道成功上报的记录，不能感知之后手动删除的本地文件。重复上报、重拍和raw副本不重复增加标准位置数。

## 接口契约

挂牌接口路径保持 `/api/v1/field-tags/{code}/`，新增 `schema_version:2`、`planting_entry_id`、`planting_plan_id`、`current_material_no`。新客户端读取 `global_material`、`membership`、`planting_population`、`section`；旧 `material` / `population` 仅保留兼容含义，不用于判断本次归属。明确为null的群体和成员合法；缺失新字段或身份矛盾时停止。

进度接口仍为 `/api/v1/capture-progress/me/`、`contexts/`、`batch/`。batch的新版每条记录在原字段之外增加：`schema_version:2`、`planting_entry_id`、`planting_plan_id`、`global_material_id`、`membership_id`、`planting_population_id`、`section_id`；后3项允许null但必须提供。`field_tag_code`必填，`accession_no`是当前编号，不含“_行…”后缀。服务端以挂牌查出的种植行为权威核验身份，保持accepted/duplicate/rejected逐条响应与旧队列幂等。

服务器进度按种植行ID及采集类型计算，再按年份、地点、本次群体汇总。缺少具体田间行的旧记录单列待核实，不自动分摊。

## 升级验收

先部署平台，再分发2.5客户端。运行 `python -m unittest discover -s tests -v`；Windows构建及125%/150%缩放测试通过后，现场核对扫码/手输→可读目录和命名→10张→另一重复行从头开始→断网及重启补传。无相机自动测试不代替MVS Runtime和真实相机验收。
